The search for ""chrome://inspect/#remote-debugging" 404 /json/version OR /json/list" returned the following summary:
A **404 error** when accessing `/json/version` or `/json/list` while using `chrome://inspect/#remote-debugging` generally indicates that the Chrome DevTools Protocol (CDP) HTTP discovery endpoints are either not exposed in your specific Chrome configuration, or you are running an environment where these endpoints are restricted[1][2][3].

Here is how to troubleshoot and resolve this issue:

### 1. Ensure a Clean, Isolated Instance
If you attempt to launch Chrome with the `--remote-debugging-port=9222` flag while another instance of Chrome is already running (e.g., your default browser), the new instance will likely fail to start with remote debugging enabled because it shares the same user profile[4][5].

*   **The Fix:** Use a dedicated user data directory for your debugging session to avoid conflicts[6][4].
    ```bash
    # Replace the path with a folder on your system
    google-chrome --remote-debugging-port=9222 --user-data-dir=/tmp/chrome-debug-profile
    ```
*   **Verify:** After launching with this command, visit `http://localhost:9222/json/version` in your browser. If successful, you will see a JSON response containing browser information[3].

### 2. Understand "WebSocket-Only" Remote Debugging
In newer versions of Chrome, the `chrome://inspect/#remote-debugging` UI toggle may enable a "WebSocket-only" mode that does not expose the traditional `/json` HTTP discovery endpoints[7][2].

*   **The Problem:** If you are using an automation tool (like an MCP server or `agent-browser`) that expects these endpoints to be available, it will fail with a 404[7][3].
*   **The Workaround:** 
    *   Check if your tool supports connecting directly via a WebSocket URL[7]. 
    *   Look for a file named `DevToolsActivePort` in your Chrome profile directory[7][8]. This file contains the port and the specific WebSocket path (e.g., `/devtools/browser/<uuid>`) needed to connect manually[7][9].

### 3. Check for Version Mismatches
If you are debugging a remote device (like an Android phone), a 404 error often occurs when the version of Chrome on the host machine is incompatible with the version on the remote device[10][11].

*   **The Fix:** Look for an **"Inspect fallback"** option on the `chrome://inspect/#devices` page[10][12]. This option is often available when there is a version mismatch and can bypass the 404 error by using a different inspection bridge[13][12].

### 4. Summary Checklist
*   **Close all running Chrome instances** before starting your debug session[3][5].
*   **Always use a custom `--user-data-dir`** to prevent the "singleton" behavior of Chrome from blocking your debug flag[6][4].
*   **Verify connectivity:** If `curl http://127.0.0.1:9222/json/version` returns 404 but the port is open, your Chrome instance is likely in "WebSocket-only" mode[3]. You may need to update your client software to a version that supports direct WebSocket connection or supports falling back to the `DevToolsActivePort` file[7][9].
